Logic Explanation - Phase 4

External Synchronization: Phase 4 extends the application boundary beyond the browser. The syncToServer() function sends the full state object — lootArray and partySize — to the server as a JSON payload using a POST request. It does not mutate state or call updateUI().

Server Load Lifecycle: When loading from the server, the app follows a strict order: Fetch → Validate → Assign → Save (local) → updateUI(). Data is never blindly assigned. Each loot item is individually inspected before anything is written to lootArray.

Validation Discipline: The loadFromServer() function validates every field of the returned state before any assignment. If any part of the response is malformed, the existing in-memory state is preserved. No partial writes are allowed.

Architectural Integrity: External sync does not replace localStorage — it extends it. Local persistence keeps the app fast and offline-capable. The server is a storage boundary only. lootArray and partySize remain the single source of truth at all times.

Separation of Concerns: Sync functions handle only communication. Mutation, persistence, and rendering remain separate responsibilities — exactly as in Phase 3. No architectural contracts were broken to add server support.
